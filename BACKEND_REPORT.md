# Отчёт о реализации backend системы подбора event-подрядчиков

Дата: 23 сентября 2026 года.

Ветка: `backend/ksusha`.

Commit реализации: `50c4ae9`.

Документ описывает фактически реализованный backend и причины технических решений. Он не вводит новых требований и не заменяет [CONTRACT.md](CONTRACT.md) — единственный контракт проекта.

## 1. Результат работы

Реализован backend, который принимает параметры мероприятия, выбирает из исходного каталога до трёх подходящих подрядчиков и возвращает JSON с персональными объяснениями.

Backend отвечает за:

- загрузку и проверку исходного dataset;
- хранение каталога в SQLite;
- модели подрядчика и запроса;
- валидацию входных параметров;
- обязательные фильтры;
- воспроизводимое ранжирование;
- подготовку подтверждающих фактов — evidence;
- опциональный AI-выбор фрагмента описания;
- проверку ответа AI и резервное формирование объяснений;
- JSON API, диагностику отказов и автоматические тесты.

Ключевой принцип реализации: допуск кандидатов и их порядок определяет Python. AI работает только с объяснениями уже выбранных кандидатов.

## 2. Использованные технологии и причины выбора

| Технология / инструмент | Где используется | Почему выбран |
| --- | --- | --- |
| Python 3.13 | Весь backend | Версия задана контрактом; стандартная библиотека покрывает модели, CSV, SQLite, даты и точные вычисления |
| Flask | Создание приложения, маршруты, JSON-ответы, обработка ошибок | Соответствует контракту и позволяет реализовать небольшой modular monolith без лишней инфраструктуры |
| SQLite и стандартный модуль `sqlite3` | Локальный каталог, поиск по городу и категории | Для 66 профилей достаточно встроенной БД; отдельный сервер не нужен, доступны транзакции и параметризованные запросы |
| CSV и модуль `csv` | Импорт исходных данных | Сохраняется предоставленный формат; для такой схемы не требуется pandas |
| `dataclasses` с `frozen=True` и `slots=True` | Модели подрядчика, запроса и evidence | Явные поля, компактные объекты и защита от случайного изменения данных между стадиями |
| `fractions.Fraction` | Расчёт ranking score | Точные рациональные вычисления уменьшают риск различий при сравнении близких оценок |
| Регулярные выражения и словарь основ слов | Проверка даты, лексический сигнал описания, выделение evidence | Даёт простой воспроизводимый анализ текста без внешней модели и загрузки embeddings |
| `httpx` | HTTP-клиент внешнего AI-провайдера | Поддерживает асинхронные запросы, потоковое чтение, таймауты и mock transport для тестов |
| `asyncio` | Общий deadline AI-запроса | Ограничивает весь вызов, включая ожидание и чтение ответа |
| Переменные окружения | Пути к данным и runtime-настройки AI | Конфигурация отделена от кода, секрет не требуется хранить в репозитории |
| pytest | Unit- и backend integration-тесты | Удобные fixtures, параметризация граничных случаев и изолированная проверка отказов |
| Ruff | Статическая проверка Python-кода | Находит ошибки и проблемы импортов до запуска приложения |
| Black | Форматирование | Поддерживает единый стиль файлов и упрощает review |

При финальной проверке использовались Python **3.13.15**, Flask **3.1.3**, httpx **0.28.1**, pytest **8.4.2**, Ruff **0.16.8** и Black **26.5.1**. Диапазоны runtime-зависимостей записаны в `requirements.txt`, инструменты проверки — в `requirements-dev.txt`.

## 3. Архитектура и организация кода

Использован modular monolith: одно приложение с разделением ответственности по модулям.

```text
JSON request
    ↓
Validation
    ↓
City + category discovery
    ↓
Hard filters + rejection diagnostics
    ↓
Deterministic ranking
    ↓
Top ≤ 3 candidates
    ↓
Evidence builder
    ↓
Optional AI reason selection
    ↓
Response validation / deterministic fallback
    ↓
JSON response
```

| Модуль | Реализованная ответственность |
| --- | --- |
| `app/__init__.py` | Фабрика `create_app`, подключение репозитория, AI-клиента, сервиса и API |
| `app/config.py` | Чтение runtime-конфигурации |
| `app/models/` | Неизменяемые модели и проверка входного запроса |
| `app/repositories/catalog.py` | Проверка CSV, создание SQLite snapshot и поиск кандидатов |
| `app/services/filters.py` | Проверка hard constraints |
| `app/services/ranking.py` | Детерминированная оценка и сортировка |
| `app/services/evidence.py` | Подготовка фактов и фрагментов описания |
| `app/services/explanation.py` | Проверка выбора AI и сборка объяснений |
| `app/services/recommendation.py` | Оркестрация полного pipeline |
| `app/ai/` | Prompt и HTTP transport внешней модели |
| `app/api/` | JSON-маршруты и ошибки валидации |
| `tests/unit/` | Изолированные проверки компонентов |
| `tests/integration/` | Проверка взаимодействия Flask, сервиса, каталога и AI-слоя |
| `scripts/demo.py` | Воспроизводимые запросы к запущенному HTTP-серверу |

Бизнес-логика вынесена из маршрутов. Это позволяет frontend использовать тот же `RecommendationService`, не дублируя фильтры и ranking.

## 4. Dataset и хранение

### Что исследовано и сохранено

В проект добавлена неизменённая копия исходного CSV: `data/hackathon_dataset.csv`. Совпадение с предоставленным файлом проверено по SHA-256.

| Характеристика | Значение |
| --- | --- |
| Профили / уникальные ID | 66 / 66 |
| Города | Алматы — 50, Астана — 15, Зарубежье — 1 |
| Категории | 17 различных значений |
| Мультикатегорийные профили | 13 |
| Synthetic-профили | 13 |
| `city_imputed=True` | 8 |
| `price_imputed=True` | 18 |
| Пустой `max_hours` | 9 |
| Цена «от» | От 100 000 до 6 000 000 ₸ |

Списки `categories`, `event_formats`, `languages` и `busy_dates` разбираются по разделителю `|`. Значения `True/False` преобразуются в boolean. Пустой `max_hours` становится `None`.

### Проверка данных

Загрузчик проверяет состав колонок, обязательные значения, уникальность ID, города, типы флагов, цены, длительность и календарные даты. Некорректный или пустой dataset останавливает запуск, чтобы приложение не выдавало рекомендации по повреждённым данным.

Модель `Contractor` дополнительно проверяет свои инварианты. Поэтому некорректные значения отклоняются и при прямом создании модели, и при восстановлении объекта из SQLite.

### SQLite

Создаются две таблицы:

- `contractors`: ID, город и JSON-представление полного профиля;
- `categories`: связи подрядчика с категориями.

Используются первичные ключи, внешний ключ, индексы по городу и категории. Значения в SQL передаются параметрами.

При старте валидированный CSV атомарно заменяет содержимое каталога. Ошибка в транзакции не оставляет частично импортированные данные. Каждая операция использует собственное соединение с SQLite.

**Почему так:** отдельная таблица категорий упрощает поиск мультикатегорийных профилей, а JSON payload сохраняет исходные поля без сложной схемы из множества таблиц. База служит восстанавливаемым snapshot CSV.

## 5. Валидация запроса

Вход должен быть JSON-объектом. Проверяются обязательные поля, типы, длины строк, корректность календарной даты и числовые границы.

Особенности реализации:

- обязательны `city`, `event_date`, `event_format`, `category`, `budget_kzt`;
- дата принимается в формате `YYYY-MM-DD`;
- бюджет — целое неотрицательное число, boolean не принимается как число;
- optional `duration_hours` — положительное конечное число;
- optional `language` — непустая строка;
- отсутствие optional-параметров или `null` отключает соответствующие ограничения;
- ошибки нескольких полей собираются вместе;
- malformed JSON и превышение лимита тела запроса 16 KiB обрабатываются контролируемо;
- ошибки валидации возвращаются с HTTP 422 и кодом `VALIDATION_ERROR`.

**Почему так:** некорректные параметры отсеиваются до обращения к ranking и AI; клиент получает понятные ошибки по полям.

## 6. Обязательные фильтры и диагностика

| Условие | Как реализовано |
| --- | --- |
| Город | Точное совпадение города кандидата и запроса |
| Категория | Запрошенная категория входит в `categories` |
| Доступность | Дата отсутствует в `busy_dates` |
| Бюджет | `price_from_kzt <= budget_kzt` |
| Формат | Значение входит в `event_formats` |
| Длительность | Если запрос задан и `max_hours` не `None`, требуется `duration_hours <= max_hours` |
| Язык | Если запрошен, должен входить в `languages` |

После поиска репозиторием сервис повторно проверяет город и категорию. Evidence builder также отказывается работать с недопустимым кандидатом.

Нарушения учитываются по причинам: `busy`, `over_budget`, `wrong_format`, `duration_too_long`, `language_mismatch`. Один профиль может увеличить несколько счётчиков.

**Почему так:** пользователь видит причины отсутствия подходящих подрядчиков, а высокий score никогда не компенсирует занятость или превышение бюджета.

## 7. Детерминированное ранжирование

Ranking применяется только к кандидатам, прошедшим все фильтры.

Текущая формула:

```text
score = 35 × budget_signal
      + 45 × description_signal
      + 10 × language_signal
      + 10 × duration_signal
```

| Сигнал | Реальное поведение |
| --- | --- |
| Бюджет | Отношение цены «от» к бюджету; при прочих равных предпочитает большее использование доступного бюджета. Для нулевого бюджета у допустимого бесплатного кандидата сигнал равен 1 |
| Описание | Среднее двух ограниченных лексических показателей: совпадения основ слов формата и категории |
| Язык | 1 при явно запрошенном и поддерживаемом языке, иначе 0 |
| Длительность | При заданном запросе — отношение запрошенных часов к `max_hours`; при `max_hours=None` — 1; при отсутствии запроса — 0 |

Все сигналы допустимых кандидатов находятся в диапазоне от 0 до 1. При отсутствии optional-параметров веса не перераспределяются. Языковой сигнал одинаков для всех прошедших этот hard filter кандидатов и сам по себе не различает их.

Сортировка: score по убыванию, затем `id` по возрастанию. После сортировки выбираются максимум три профиля.

**Почему так:** формула прозрачна, воспроизводима и не сводится к цене. Использование `Fraction` и явного tie-breaker обеспечивает устойчивый порядок. Лексический сигнал является простой эвристикой, а не обученной моделью качества подрядчиков; его веса не калибровались на пользовательских оценках.

## 8. Evidence и AI-объяснения

### Подготовка evidence

Для каждого финального кандидата формируются:

- ID и запрошенная категория;
- город, дата и подтверждённая доступность;
- цена «от» и бюджет;
- совпавший формат;
- optional-язык и данные о длительности;
- исходное описание;
- до шести конкретных фрагментов описания с собственными `reason_id`.

Фрагменты сохраняются как исходные подстроки. Отбор предпочитает конкретные услуги, оборудование и опыт. Для отсеивания рекламных фраз используются эвристики. Если подходящих фрагментов нет, объяснение строится из проверенных структурированных фактов.

### Что делает AI

Внешняя модель получает одним запросом evidence только финальных ≤3 кандидатов. Она выбирает для каждого кандидата один допустимый `reason_id`, который лучше объясняет соответствие запросу.

AI не создаёт финальный свободный текст. Python проверяет выбранные ссылки на evidence и собирает 1–2 русских предложения из точных фактов и цитаты.

Проверяются:

- структура ответа;
- точный состав ID кандидатов;
- отсутствие повторов и посторонних кандидатов;
- принадлежность выбранного фрагмента конкретному кандидату;
- отсутствие дополнительных неподтверждённых полей.

**Почему так:** произвольную прозу сложно надёжно проверить на выдуманные факты. Ограниченный выбор evidence оставляет AI задачу семантического выбора и сохраняет программный контроль над фактами. Ответ модели не может изменить eligibility или порядок карточек.

### Работа при отказах

При отсутствии AI-конфигурации, timeout, HTTP-ошибке, malformed JSON или недопустимом выборе применяется deterministic fallback: первый фрагмент после локального ранжирования и точные факты кандидата.

Защитные настройки transport:

- один batch-вызов без повторных попыток;
- общий deadline по умолчанию 3 секунды;
- `temperature=0`;
- JSON-формат ответа;
- ограничение ответа 64 KiB;
- запрет автоматических redirect;
- ошибки провайдера не выводятся в API и не логируются кодом fallback.

Цена в объяснении указывается как «от». Отсутствие `max_hours` объясняется как непривязанность услуги к длительности присутствия, а не обещание безлимитной работы.

## 9. JSON API и интеграция frontend

Реализованы маршруты, предусмотренные разделом 13 [CONTRACT.md](CONTRACT.md):

| Маршрут | Назначение |
| --- | --- |
| `GET /api/v1/health` | Проверка доступности запущенного приложения |
| `POST /api/v1/recommendations` | Подбор подрядчиков по параметрам мероприятия |

Различаются три результата:

- `matched` — от одной до трёх карточек;
- `category_not_found` — нет профилей соответствующего города и категории;
- `no_eligible_candidates` — профили найдены, но все отклонены; возвращаются агрегированные причины.

Карточки сохраняют `synthetic`, `city_imputed` и `price_imputed`. Если карточек меньше трёх, сообщение поясняет, что показаны все прошедшие условия кандидаты.

Frontend может использовать общий сервис через:

```python
app.extensions["recommendation_service"].recommend(payload)
```

Варианты полей формы можно получить из `app.extensions["catalog_repository"].all()`. Фабрика приложения допускает подстановку репозитория и AI-клиента для тестирования.

## 12. Границы выполненной работы

- HTML-форма, оформление карточек, визуальные badges и браузерные E2E относятся к интеграции с `frontend/denis` и в backend не реализовывались.
- Реальный запрос к внешнему AI-провайдеру с предоставленным credential не выполнялся. Transport и AI success/failure проверены через mock transport и подставные клиенты.
- Ranking основан на прозрачных эвристиках; embeddings, vector database и обученный recommender не используются.
- AI-интерфейс вызывается из синхронного Flask pipeline; отдельная интеграция с async web routes не реализована.
- Проверка качества подтверждает backend-сценарии. Полный project gate с UI проверяется после объединения frontend и backend.

Redis, Celery, микросервисы и отдельный сервер БД не добавлялись: размер каталога и синхронный запрос не требовали такой инфраструктуры.
